[experimental] `astryx experimental render`: an https image the page shows only later (after a click, in the next view) is carried too, when the page's own code writes its address whole. That means an address whose path ends in an image extension, the value of a JSX `src`, `srcSet` or `poster`, or the value of a property or attribute one of whose words names an image (`avatarUrl`, `cover_image`; not `logoutUrl`). It is fetched with the same rules and limits as an image in the first paint, listed in `remoteImages`, and the file's script draws it from the carried data, so it shows offline. A link's address written in `href`, directly or through a variable named there, is never fetched, even when it names an image file. An address that counts only by an image word in a name around it (`imageUploadUrl`) can be an API's: when its answer is another type (an API's JSON, a page), the page keeps the address as written, with no warning, and `remoteImages.failed` lists it with why. Any other address the script draws later warns when its fetch fails, as in the first paint. No other address is fetched. An image address the code builds from parts right where an image goes (a template or `+` chain that starts with `https://`, in a `src`, `srcSet`, `poster` or image-named property), or one the code hands to the URL API (`new URL(photo)`, also through a variable, a property or a helper's parameter), is kept as written and gets a `remote-asset` warning that names it, its file and its line; one built elsewhere is neither carried nor warned.
